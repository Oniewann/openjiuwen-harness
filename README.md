# Бюджетный харнесс кодового агента на openJiuwen

Решение для openJiuwen Challenge: харнесс получает каталог задач и бюджет токенов и набирает
максимум баллов, тратя как можно меньше. Замеры на наших наборах и настоящих моделях —
в разделе «Состояние».

## Запуск

```
docker build -t hack:latest .
docker run --rm --network hack-net -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET \
  -v "$TASKS:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

Ответ пишется в `<задача>/answer.txt` (рядом с `task.json`) сразу после решения. Для задачи,
признанной невыполнимой, файл не создаётся. Из `task.json` читаются только `task_id`, `task_type`,
`instruction`, `reward` (см. `harness/tasks.py`); поля `expected` и `check` харнесс не читает.

## Как устроено

Каждая задача проходит лестницу от бесплатного к дорогому (`harness/solvers/`):

1. **Навык, 0 токенов** (`harness/skills/`): строгий разбор типовых задач — цепочки по базе знаний,
   сравнение двух записей по году и обратные ссылки («кого наставляет X»); агрегаты по csv с фильтрами,
   округлением и выручкой (`units × price`); текстовые задачи про запас (проценты, «сколько отгружено
   всего»); ремонт кода: сначала эталонные реализации типовых функций, затем перебор мутаций с проверкой
   тестами (см. «Coding и скрытые тесты»). Навык либо уверен, либо отказывается
   (каждое слово вопроса должно быть объяснено). Организаторы разрешили решать без LLM.
2. **Дешёвая модель без рассуждений**: один вызов, модель пишет короткое выражение Python над уже
   загруженными данными (`rows`, `kb`), считает харнесс (`harness/pot.py`). Для coding модель
   присылает только изменённые функции, харнесс применяет их и запускает тесты.
3. **Вторая дешёвая модель** — независимая перепроверка ответа, у которого нет программной проверки.
4. **Модель с рассуждениями** — арбитр при расхождении и последняя попытка.
5. **ReAct-агент openJiuwen с bash** в копии каталога задачи — для незнакомых задач.

### Как используется openJiuwen

Это харнесс над openJiuwen: модели вызываются только через openJiuwen, а навыки и планировщик решают,
когда и с каким вводом их вызывать.

```
run_agent.py → harness/runner.py
  Scheduler (scheduler.py): следующий шаг = max(шанс × баллы / стоимость)
   ├─ навыки (skills/, 0 токенов) — детерминированные инструменты: решают типовые задачи сами,
   │   готовят данные для модели (rows, kb, упавшие тесты) и проверяют её ответы
   ├─ MathSolver / DataSolver / SearchSolver / CodingSolver (solvers/) → LLMHub.call
   └─ ступень 5: openjiuwen ReActAgent + инструмент @tool("bash") (solvers/react.py),
       agent.set_llm(hub.model()) — тот же объект модели
                │
  LLMHub (llm.py): резерв худшего случая, max_tokens ≤ остаток, потолок задачи, лимит одновременных запросов
                │
  MeteredModel (наследник openjiuwen Model) → Model.invoke → OpenAI-совместимый прокси
                │
  Ledger (ledger.py): usage → «вход/10 + выход» → report.json
```

Каждый вызов модели — и прямой из решателей, и изнутри `ReActAgent` — проходит через
`MeteredModel.invoke` (`harness/llm.py`), поэтому учёт расхода и лимиты харнесса не обойти.

### Coding и скрытые тесты

Проверяющие тесты могут быть шире видимых, а перебор мутаций принимает первую правку, с которой проходят
видимые: `range(n)` → `range(1, n)` чинит `fib(10) == 55` и ломает `fib(0)`. Поэтому:

- `harness/skills/semantic.py`: для ~110 типовых имён функций (`total`, `maximum`, `reverse_words`, `fib`, …)
  есть эталоны. Поведение функции сравнивается с эталоном на пробных входах, построенных из вызовов в
  тестах (пустой список, один элемент, отрицательные числа, …). Расходящаяся функция заменяется эталоном,
  только если от этого строго уменьшается число упавших тестов; у неоднозначных имён (`average`: `/` или
  `//`) берётся вариант, проходящий тесты и ближайший по тексту к исходнику. Это 0 токенов и не зависит от
  вида бага (синтаксическая ошибка, пропавший `return`, заглушка `pass`, отсутствующая функция).
- Для функций с незнакомыми именами работает перебор мутаций. Его правка сразу записывается (тесты проходят),
  а затем одной дешёвой попыткой модели проверяется: модель чинит исходный код независимо, и если её версия
  проходит те же тесты, но ведёт себя иначе на пробных входах, берётся версия модели (`HARNESS_CODE_CROSSCHECK`).
- Без модели закрываются задачи, где тесты не могут пройти: противоречивые ожидания одного вызова,
  `assertEqual(1, 2)`, синтаксическая ошибка в самом тесте, отсутствие файла тестов.

### Вид ответа

Модель без рассуждений нередко пишет выражение «почти про то»: сравнение вместо имени, год вместо человека,
разность с обратным знаком. Ожидаемый вид ответа виден из вопроса, поэтому результат выражения проверяется
бесплатно (`ExprSolver.shape_answer`): `True`/`False` на вопрос «Which company…» возвращается модели с
замечанием, на вопрос «Do … ? Answer yes or no» превращается в `yes`/`no`.

### Оценка расхода (`harness/estimator.py`)

Стоимость шага оценивается до запуска: вход известен почти точно (промпт уже собран), выход —
линейная модель по типу задачи и простым признакам; обе части уточняются на ходу по фактическому
`usage`. Модель саму себя о стоимости не спрашиваем.

### Планировщик (`harness/scheduler.py`)

В каждый момент выполняется шаг с наибольшей отдачей на токен: `шанс × баллы / стоимость`. Сначала
всё бесплатное, затем дешёвые попытки (дорогие по баллам задачи раньше), эскалации — только если
шанс оправдывает цену и шаг влезает в остаток бюджета.

Бюджет берётся из переменной `BUDGET` любой величины и в любой записи (`100000`, `1e5`, `100k`); лимиты
на задачу и «курс» токенов за балл масштабируются от бюджета и числа задач, каждый вызов резервирует
худший случай и ограничивает `max_tokens` остатком, так что харнесс останавливается сам, не выходя за бюджет.

К модели одновременно идёт не больше 3 запросов (`HARNESS_PARALLEL`, максимум 5). Ответ 429 «слишком много
одновременных запросов» не считается сбоем: харнесс ждёт, сужает параллельность и повторяет вызов; 429 с
текстом об исчерпании бюджета останавливает вызовы модели. Неудачный вызов списывается по оценке входа
(вход/10).

### Невыполнимые задачи

- без модели: человека нет в базе, цепочка ссылок обрывается, значение поля — «unknown», нет файла,
  в условии нет числа, тесты не могут пройти (противоречие, `assertEqual(1, 2)`, ошибка в самом тесте);
- «нет столбца» больше не закрывает задачу без модели: столбец могут назвать иначе, поэтому одна дешёвая
  попытка модели подтверждает отказ;
- моделью: в каждом промпте разрешён ответ `IMPOSSIBLE` / `NOT_FOUND`; два независимых отказа —
  задача закрывается;
- по ходу: каждая неудача снижает оценку «задача выполнима» (байесовский пересчёт), и дорогие
  ступени не запускаются; на задачу есть потолок токенов.

## Собранные траектории

Харнесс пишет траекторию каждого прогона в `report.json` (каждые 20 с и в конце; по умолчанию
`/tmp/harness-<pid>/`, каталог задаёт `HARNESS_TRACE_DIR`): `summary` (ответы, статусы, расход, причина
остановки), `ledger` (вызовы и токены по моделям), `estimator` (поправки оценщика за прогон),
`calls` (каждый вызов: задача, ступень, модель, `prompt`/`completion`/`reasoning` токены, стоимость, время,
ошибка) и `tasks` — по каждой задаче статус, ответ записан или нет, расход, голоса, отказы, вывод
статической проверки и `trace`: шаги по порядку (навык, вызов модели, исход с прогнозом стоимости и
фактом). `HARNESS_TRACE_TEXT=1` добавляет тексты ответов модели (обрезаны до 600–800 символов; только
для локальных прогонов). `devtools/trial.py` сверяет отчёт с эталонами.

**Как использовали.** По траекториям выставлены априорные значения оценщика (`DEFAULT_MODEL` в
`harness/estimator.py`: длина ответа по типу задачи, токены рассуждений, доля успехов ступеней; подгонка
ручная, в прогоне они уточняются по факту) и разобраны ошибки моделей — из них выросли проверка вида
ответа (`shape_answer`) и выводы раздела «Состояние». Ещё найдено: после замечания харнесса модель забывает право ответить
`IMPOSSIBLE` и подставляет выдуманные данные; `-noreason` модель отвечает на вопрос по базе списком
имён, которых в базе нет; две дешёвые модели часто ошибаются одинаково (первые ответы совпали
посимвольно в 32 случаях из 90, в том числе в ошибках), так что их совпадение — слабая проверка.

**Примеры** (8 примеров организаторов, 2026-11-13; поля сокращены):

```
# 1. Навык, 0 токенов (--no-llm). search_0005: «In which city is the headquarters of Sergei Garcia's employer?»
{"step": "skill", "answer_by": "skill", "detail": "Sergei Garcia > Employer > Headquarters"}
# → 'Osaka' (verified), spent 0; весь прогон без модели: 8/8, 0 токенов, 0,4 с

# 2. Модель с первой попытки (HARNESS_FASTPATH=0, навык только сверяет). math_0000, 5 баллов:
{"step": "skill", "role": "crosscheck", "detail": "((((1752 // 2) * 2) // 3) * 2) // 3"}
{"step": "fast", "model": "qwen3.8-27b-noreason", "prompt_tokens": 190, "completion_tokens": 48, "cost": 67.0,
 "reply": "boxes = 1752\nboxes = boxes // 2\nboxes = boxes * 2\n... print(boxes)"}
{"step": "outcome", "kind": "answer", "cost": 67.0, "predicted": 51.3, "status": "verified"}  → '389'
# код модели исполняет харнесс; ответ совпал с навыком → verified. Весь прогон: 8/8, 494 токена, 9 вызовов
# (один получил от прокси 429 и был повторён, его вход учтён в расходе).

# 3. Модель после замечания харнесса (стресс-набор, невыполнимая задача «It ships N boxes per day…»):
fast:   print(1832 - 3 * N)
харнесс: That failed: NameError … Reply with the corrected code only.
fast:   N = 0 ... (дальше счёт с выдуманным N)
```

Пример 3 — та самая ошибка «забывания» отказа: задача невыполнимая, баллы не потеряны, но ответ записан и
токены потрачены.

## Состояние

Замеры 2026-11-12. Все наборы, кроме 8 примеров, сделаны нашим генератором (`devtools/gen_tasks.py`)
по образцу примеров организаторов; на скрытых задачах с незнакомыми формулировками цифры могут быть хуже.

**Без модели (только навыки):**

| Набор | Верно | Неверно | Токены |
|---|---|---|---|
| 8 примеров организаторов, **командой запуска жюри в Docker** (arm64 и amd64) | 8/8 (20/20 баллов), ~1,5 с | 0 | 0 |
| `base100`: 100 задач по шаблонам примеров | 100/100 | 0 | 0 |
| `mixed100`: 20 невыполнимых, 35% отклонений от шаблона | 80/80 выполнимых | 0 | 0 |
| 2 × 200 свежих (seed 11, 12): 20% невыполнимых, 60% отклонений | 153/160 и 152/160 | 0 | 0 |

**С настоящими моделями через прокси NeuralDeep:**

| Набор | Режим | Верно | Ответов на невыполнимые | Токены |
|---|---|---|---|---|
| 8 примеров | навыки выключены, только модель | 8/8 | — | 450 (по 1 вызову на задачу) |
| `mixed100` | навыки выключены, только модель | 80/80 | 0 | 4850 |
| 2 × 200 свежих | боевой режим (навыки + модель) | 160/160 и 160/160 | 0 | 1402 и 1216 |

Статическая проверка поймала все 100 невыполнимых задач наших наборов (6 типов: нет человека или
поля в базе, нет файла или столбца, в условии нет числа, деление на ноль, противоречивые тесты),
и ни одна выполнимая не была закрыта ею по ошибке.

**Что показали модели** (формат ответа прокси):
- `usage.completion_tokens` уже включает рассуждения (`qwen3.8-27b`: 62 = 56 рассуждений + 6 ответа);
  у `qwen3.6-35b-a3b` разбивки нет, но счёт тот же. Харнесс считает `prompt/10 + completion`, и это
  совпадает с прокси;
- на вопрос «17×23» `-noreason` модели тратят 4 выходных токена, `qwen3.8-27b` — ~62,
  `qwen3.6-35b-a3b` — ~230. Поэтому дешёвые шаги идут на `-noreason`, а рассуждения — только при эскалации;
- на `mixed100` первая дешёвая модель ни разу не ошиблась, перепроверка второй ни одного ответа не
  изменила. Перепроверку всё равно оставляем: баллы важнее токенов, а на незнакомых формулировках
  ошибки вероятнее. Основной расход — входные токены (в `mixed100` вход 18,8 тыс. = 1,9 тыс. в
  пересчёте против 2,7 тыс. выхода).

**Стресс-набор гипотез** (`devtools/stress_gen.py`): 281 гипотеза о том, чем скрытый набор может отличаться от
примеров — другие формулировки, операции, форматы файлов, виды багов, 50 видов невыполнимых задач. В coding
эталонная проверка шире видимых тестов (по 2–3 дополнительных утверждения на функцию).

| Набор | Режим | Верно | Неверно | Токены |
|---|---|---|---|---|
| 1112 задач (4 на гипотезу, зерно 21) | только навыки | 649 из 904 выполнимых | 0, ложных отказов 0 | 0 |
| из них coding | только навыки | 172 из 172 | 0 | 0 |

До правок 2026-11-12 на том же наборе гипотез навыки давали 26 неверных ответов (17 из них — починки кода,
проходившие видимые тесты и падавшие на расширенных) и 13 ложных отказов. Промахи из двух последних строк
после прогона исправлены, повторный прогон с моделью не делался.

В контейнере командой жюри (`--read-only --cap-drop ALL --pids-limit 512`): без сети — 8/8 на примерах
(arm64 и amd64) и 176/176 на стресс-наборе coding за 91 с; с прокси и выключенными навыками — 8/8, 462 токена.

Образ: сборка ~6,5 мин на медленной сети (почти всё время — скачивание пакетов), под amd64 через
эмуляцию ~8 мин; размер 1,41 ГБ (лимит 4 ГБ). Все транзитивные версии зафиксированы в
`constraints.txt` (`pip freeze` из образа).

## Разработка

```
python devtools/stress_gen.py --list                                   # 281 гипотеза о скрытом наборе
python devtools/stress_gen.py --out ../train/stress --per 4 --seed 21  # 1112 задач
python devtools/trial.py --tasks ../train/stress --no-llm --show-log 0 --out stress.json
python devtools/stress_report.py --result stress.json --meta ../train/stress.meta.json --bad --show WRONG,STATIC
STRESS_RENAME=_x python devtools/stress_gen.py --out ../train/stress_x --only coding   # функции с незнакомыми именами
python devtools/gen_tasks.py --out ../train/mixed100 --n 100 --seed 2 --infeasible 0.2 --variation 0.35
python devtools/trial.py --tasks ../train/mixed100 --no-llm          # только навыки
python devtools/trial.py --tasks ../train/mixed100 --mock oracle     # с локальной заглушкой модели
python -m unittest discover -s tests -t .
```
